Building a Spotify MCP Server: From API to AI Agent

If you’re new to MCPs, just need a refresher, or are simply curious about how they work, this guide is for you.

So, what’s MCP?

Think of MCP as a toolbox for AI agents.

Basically, MCP (Model Context Protocol) is a standardized interface that allows AI agents to interact with external services like APIs, databases and other tools.

Now, technically, an AI agent can call APIs directly. It doesn’t necessarily need MCP to do that. But here’s the thing: rather than having to figure out API endpoints, construct requests and understand different response formats every time, you can expose these operations through an MCP server.

Think about it like this. Imagine you’re a carpenter. Rather than going to the shed every time you need a tool, you have a toolbox containing the tools you need. That’s essentially what MCP provides for AI agents.

For example, take Spotify. Spotify already has a Web API, so technically, an AI agent can interact with Spotify directly through its API. But with an MCP server, we can expose Spotify’s functionality as a collection of tools that the agent can discover and use.

So instead of figuring out which endpoint to call, the agent can simply use a tool like search_tracks or create_playlist.

And there’s another advantage here. An agent can hallucinate API endpoints or parameters when working directly with APIs. With MCP, we give it predefined tools, descriptions and input schemas. This doesn’t completely eliminate hallucinations, but it makes interactions more structured and predictable.

That’s the basic idea.

Now, what I want to do here is build a simple Spotify MCP server. Nothing too complicated. Just an MVP that covers some of the things we’ll be going through: authentication, API calls, tool definitions and, importantly, how an AI agent can combine different tools to achieve a goal.

I don’t think we’ll be covering much about tool calling itself, because that’s largely handled by the MCP client and the agent. But we’ll see how everything fits together.

Alright, I’ve opened the Spotify Developer Dashboard. Let’s get straight to the main thing.

1. Setting up Spotify

Spotify is primarily an API-based service, and it provides a developer dashboard where you can create applications.

So, from the Spotify Developer Dashboard, you can create an app. Each app comes with its own credentials, mainly a Client ID and Client Secret.

These credentials identify your application when making requests to Spotify.

That’s basically the initial setup. Nothing particularly complicated here.

Now that we have that out of the way, let’s move on to authentication.

2. Authentication: Getting an Access Token

How do you actually call Spotify’s APIs?

You can’t just pick an endpoint and start making requests. Spotify needs to verify that your application is authorized to access the resources you’re requesting.

This is where OAuth comes in.

Spotify supports different authorization flows, depending on the kind of application you’re building and what you’re trying to achieve.

For this project, we’ll be using the Authorization Code with PKCE flow.

PKCE stands for Proof Key for Code Exchange. It’s an extension to OAuth 2.0 that makes the authorization process safer, particularly for applications that cannot securely store a client secret.

Now, PKCE is something that took me a while to understand properly. It can be a little obscure when you’re first encountering it, so I don’t want to spend too much time on it here.

I’ll probably drop a separate article explaining PKCE entirely, because I think it deserves its own walkthrough.

For now, let’s focus on what we actually need: getting an access token.

The general process is pretty straightforward.

First, we initiate the authorization process. Our application generates a code verifier and a code challenge, then redirects the user to Spotify’s authorization page.

The user signs in, grants the requested permissions, and Spotify redirects them back to our application with an authorization code.

We then exchange that authorization code, alongside our original code verifier, for an access token.

And that’s pretty much what we need for now.

There’s also something called scopes. Basically, scopes determine what permissions our application is requesting from the user.

For example, if we want to access a user’s playlists or create playlists on their behalf, we’ll need to request the appropriate scopes.

We shouldn’t just request every available permission. We’ll request the ones relevant to the tools we’re exposing.

Once we have our access token, we need to store it somewhere.

For local development, something like a token.json file should be sufficient.

If we’re running this in production, the setup will be slightly different. We’d need to consider more secure credential storage and token management.

But I think we’ve covered enough authentication for this article. I’ll stop at obtaining and saving the access token for now. We can handle refresh tokens and the other authentication-related stuff separately.

I don’t want to go too far off-topic.

3. Structuring the Project

Alright, so we’ve handled the initial setup and authentication. What’s next?

I’m thinking about how I want the project structured.

One thing I want to achieve is making this a proper installable package rather than just another Python script sitting in a repository.

So, I want the entry point to be through the CLI.

We’ll use Typer, by Tiangolo, to handle the command-line interface.

If you’ve used Typer before, you probably know it’s relatively straightforward to set up.

The idea is that users shouldn’t have to manually configure everything or run different Python files to get the server working.

Ideally, you should be able to run something like:

spotify-music-mcp connect

And the application handles the rest.

Let’s break down what that process would look like.

4. Building the CLI and Authentication Flow

When you run spotify-music-mcp connect, the first thing we need to handle is authentication.

We can redirect the user to their browser, where they’ll complete the Spotify OAuth process.

Once authentication is successful, we receive the access token and save it locally.

We also need to think about users who don’t necessarily want to authenticate immediately.

For example, someone might just want to install the package and add it to their AI agent’s configuration first.

So, authentication shouldn’t necessarily be compulsory during the initial setup.

We can provide a separate command for authentication, something like:

spotify-music-mcp auth login

And another command to clear the saved credentials and start the authentication process again.

Basically, I want the whole experience to be as simple as possible.

You install the package, configure it, authenticate when necessary, and connect it to your agent.

We can also handle the actual server startup through the CLI.

That’s the general idea.

5. Defining the MCP Tools

Now, let’s get to the actual MCP implementation.

Remember, the whole point of this project is to expose Spotify’s API functionality to an AI agent.

So, essentially, we’re taking Spotify API operations and making them available as MCP tools.

Think of each tool as a function the AI agent can discover and call.

For example, we could have a search_tracks tool.

This tool would accept a search query and perhaps a limit parameter. When the agent invokes it, our server takes those parameters, makes the appropriate request to Spotify’s API and returns the results.

We could also have tools for retrieving artist information, searching albums, accessing playlists and creating new playlists.

Each tool needs a few things:

  • A name.
  • A description explaining what it does.
  • The parameters it accepts.
  • The appropriate input types and validation.
  • A structured response.

The descriptions are particularly important because they’re what help the AI agent understand what each tool does and when to use it.

Now, I don’t think it’s particularly useful to manually type out every single tool definition in this walkthrough. It can get boring pretty quickly.

The implementation is mostly about connecting the different Spotify API operations to the MCP tool definitions.

You define the tools, specify their input schemas, provide descriptions and map them to the functions responsible for making the actual API calls.

So, when an agent calls a tool, the MCP server receives the request, validates the parameters, executes the corresponding function and returns a formatted response.

That’s essentially the core of the MCP server.

6. Making the Agent Combine Different Tools

There’s another thing I want to touch on here, and that’s the ability of AI agents to combine different tools to achieve a goal.

Because, really, having an agent call one tool at a time isn’t particularly interesting.

Let’s take an example.

Imagine you ask your AI agent:

“Create a playlist containing songs from my recently played music.”

How does it achieve that?

Well, it could first call a tool to retrieve your recently played tracks.

Then, it collects the results and calls another tool to create a playlist.

Finally, it calls another tool to add those tracks to the newly created playlist.

So, we’ve got different tools performing different operations, but the agent is able to combine them to achieve one objective.

That’s what makes tool use interesting.

Rather than writing one massive function for every possible task, we expose smaller, reusable tools that the agent can combine depending on what the user wants.

Of course, some operations will require additional permissions, and actions that modify a user’s Spotify account should have appropriate safeguards.

But you get the idea.

7. Packaging and Publishing

Now, remember I mentioned earlier that I want this project to be an installable package?

That’s another thing we need to work towards.

I don’t want users to clone the repository, manually install dependencies and start figuring out how everything works.

The goal is installation ease.

So, the first thing we’ll need to do is package the project properly.

We’ll build the distribution files and publish the package to PyPI.

Once it’s published, users can install and run it using tools like pipx or uvx.

We could also provide an NPX version.

Now, this doesn’t mean we’re rewriting the entire project in JavaScript.

We can simply publish a small NPM wrapper around the Python package that launches it.

That way, someone who’s more comfortable with the Node.js ecosystem can use NPX to run the server without having to manually clone the repository.

It’s an optional addition, but I think it’s a nice way to make the project more accessible.

And that’s pretty much it for the initial implementation.

8. What’s Next?

So, we’ve gone through the basic process of creating our own MCP server.

We’ve covered setting up the Spotify application, authentication, obtaining an access token, defining tools, structuring the project and packaging it for distribution.

But there’s still quite a lot we can explore.

For example, we could take this a step further and make the server remote.

Rather than having users install the package locally, we could host the MCP server and allow agents to connect through an HTTP URL.

That introduces another interesting aspect of MCP, which is remote connectivity.

We could also build something around browser automation.

For example, imagine creating an MCP server for browser-use functionality, allowing AI agents in tools like Gemini or OpenCode to interact with a browser through a standardized interface.

That’s another project I’d like to explore.

So, yeah, that’s pretty much where we’re going with this.

For now, this should give you a basic understanding of how to build an MCP server around an existing API and make it accessible to AI agents.
